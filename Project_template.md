## Задание 1. Исследование моделей и инфраструктуры

### Контекст решения

Для QuantumForge Software нужен внутренний RAG-бот, который ищет ответы в корпоративной базе знаний, помогает сотрудникам быстрее находить актуальные документы и снижает нагрузку на тимлидов, поддержку и GRC-команду. Важные требования: качество поиска, контролируемая стоимость, возможность работы с конфиденциальными документами и понятная эксплуатация.

### Сравнение LLM

| Вариант | Качество ответов | Скорость | Стоимость | Развёртывание | Вывод |
| --- | --- | --- | --- | --- | --- |
| Локальные Hugging Face модели | Зависит от модели и железа; хорошие результаты требуют крупных моделей | На CPU медленно, на GPU приемлемо | Нет платы за токены, но нужна инфраструктура | Сложнее: GPU, мониторинг, обновления | Подходит для конфиденциальных данных и полного контроля |
| OpenAI-совместимые облачные модели | Высокое качество рассуждений и следования инструкциям | Обычно высокая | Оплата за токены | Простое API-подключение | Лучший старт для MVP, если данные можно отправлять во внешний API |
| YandexGPT | Хорошая поддержка русского языка и облачная эксплуатация | Высокая | Оплата за использование | Простое API-подключение | Хороший вариант для русскоязычного интерфейса и локального облака |

### Сравнение моделей эмбеддингов

| Вариант | Скорость индексации | Качество поиска | Стоимость | Вывод |
| --- | --- | --- | --- | --- |

| Sentence-Transformers `bge-base-en` | Средняя | Обычно выше качество семантического поиска | Бесплатно, но тяжелее | Подходит для следующей итерации качества |
| OpenAI Embeddings | Высокая через API | Высокое качество на разных доменах | Оплата за токены | Хороший вариант для продакшена при допустимости облака |

### Сравнение векторных баз

| Вариант | Скорость | Поддержка | Удобство | Стоимость | Вывод |
| --- | --- | --- | --- | --- | --- |
| FAISS | Очень быстрый локальный поиск | Нужно самостоятельно хранить метаданные | Простая библиотека, хорошо подходит для файлового индекса | Бесплатно | Выбран для MVP: минимальная инфраструктура и быстрый старт |
| ChromaDB | Хорошая для небольших и средних баз | Есть коллекции, метаданные, persist-хранилище | Удобнее для разработки приложений | Бесплатно, но нужен отдельный слой хранения | Хороший вариант, если нужны коллекции и фильтры без ручной обвязки |
| Qdrant | Высокая, production-ready | API, фильтры, снапшоты, масштабирование | Требует сервиса или контейнера | Бесплатный self-hosted, есть managed | Рекомендуется для промышленной версии после MVP |

### Варианты инфраструктуры

| Вариант | Конфигурация | Плюсы | Минусы | Для чего подходит |
| --- | --- | --- | --- | --- |
| Минимальный MVP | 2 CPU, 4 GB RAM, без GPU | Дёшево, достаточно для FAISS и FastAPI | Ограниченная скорость генерации локальных моделей | Учебный проект и демо |
| Корпоративный MVP | 4 CPU, 8-16 GB RAM, без GPU | Запас по памяти, стабильная индексация | LLM остаётся облачной | Первая внутренняя версия |

| Production RAG | Kubernetes, отдельный vector DB, мониторинг, секреты в vault | Масштабирование и надёжность | Выше сложность внедрения | Массовое использование в компании |

### Итоговая рекомендация

Для текущей проектной работы выбран стек: FastAPI, FAISS, локальные эмбеддинги Sentence-Transformers и облачная LLM через API. Такой вариант быстро реализуется, не требует отдельного сервиса векторной БД и позволяет показать полный RAG-пайплайн. Для промышленной версии QuantumForge Software стоит рассмотреть Qdrant, SSO, разграничение доступа к документам, аудит запросов и хранение секретов во внешнем secret manager.

## Задание 2. Подготовка базы знаний

Для базы знаний используется вымышленная корпоративная вселенная `AetherOps`, построенная по мотивам открытых sci-fi справочников, но с заменой ключевых сущностей на искусственные названия. Итоговая база хранится в папке `knowledge_base/`, а словарь замен — в `data/terms_map.json`. Документы разбиты по сущностям: персонажи, планеты, технологии, регламенты, события и инфраструктурные объекты.

## Задание 3. Создание векторного индекса

Индекс строится скриптом `scripts/build_index.py`. Документы разбиваются на чанки по 500-1000 символов с перекрытием, для каждого чанка сохраняются метаданные: путь к источнику, заголовок, номер чанка и текст. Основной режим использует Sentence-Transformers и FAISS, а fallback-режим сохраняет совместимый JSON-индекс с детерминированными локальными эмбеддингами.

Фактическая сборка для репозитория: 31 документ, 61 чанк, модель `hashing-fallback-384`, размерность 384, время сборки около 0.02 секунды. Пример поискового запроса «Кто отвечает за HelioBridge?» возвращает документ `knowledge_base/heliobridge.md` первым результатом.

## Задание 4. Реализация RAG-бота

RAG-бот реализуется как REST API на FastAPI. Endpoint `/ask` принимает вопрос, ищет релевантные чанки, фильтрует потенциально опасные инструкции из документов, формирует промпт с few-shot примерами и возвращает ответ с источниками. Облачная LLM подключается через переменные окружения; без API-ключа работает локальный extractive fallback для демонстрации пайплайна.

## Задание 5. Запуск и демонстрация работы бота

Для проверки prompt injection добавлен отдельный вредоносный документ в демонстрационную базу. Защита состоит из системной инструкции, фильтрации опасных шаблонов в найденных чанках и отказа отвечать при низкой релевантности. Демонстрационные запросы и ожидаемые результаты лежат в `demo/demo_queries.md`.

Фактический лог демонстрации с `gemini-flash-latest` сохранён в `demo/gemini_demo_results.md`: 5 успешных ответов с источниками и 5 корректных отказов «Я не знаю».

## Задание 6. Автоматическое ежедневное обновление базы знаний

Автоматическое обновление реализуется скриптом `scripts/update_index.py`: он проверяет изменения в `knowledge_base/`, пересобирает индекс, пишет лог и может запускаться по cron. Диаграмма архитектуры находится в `diagrams/update_flow.puml`.

## Задание 7. Аналитика покрытия и качества базы знаний

Для оценки качества используются `data/golden_questions.jsonl` и `scripts/evaluate.py`. Каждый запрос логируется с текстом вопроса, временем, статусом ответа, длиной ответа и найденными источниками. Диаграмма обработки запроса находится в `diagrams/evaluation_sequence.puml`.

Фактический результат автоматической оценки: 12 вопросов, 12 успешных проверок, покрытие golden set — 100%. Выявленные пробелы: в базе нет HR-данных и зарплат, нет произвольных событий вроде чемпионатов, а запросы секретов и prompt injection намеренно фильтруются.

## Запуск проекта

1. Создать окружение и установить зависимости: `python -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt`.
2. Сгенерировать базу знаний: `python scripts/generate_knowledge_base.py`.
3. Построить индекс: `python scripts/build_index.py`.
4. Запустить API: `uvicorn src.api:app --reload`.
5. Отправить вопрос: `curl -X POST http://127.0.0.1:8000/ask -H "Content-Type: application/json" -d '{"question":"Кто отвечает за протокол HelioBridge?"}'`.
